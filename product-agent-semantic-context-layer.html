Context Layer

A living semantic context layer that learns unfamiliar databases, compresses large schemas into meaningful business concepts, validates only high-impact uncertainty, and serves trusted task-specific context to AI agents.

01

Executive summary

The product is a continuous reasoning system, not a schema-documentation generator.

Core promise

Teams building AI agents over customer-owned databases should not have to understand hundreds of tables manually or expose raw schemas directly to an agent. Atlas turns the database into a small, evidence-backed reasoning surface shaped by the agent’s objective.

02

Problem and target user

AI teams integrating databases they do not own are forced into one of two weak interfaces.

Failure mode A

Raw schema and unrestricted SQL

Hundreds of tables, inconsistent names, stale descriptions, implicit business rules, overlapping fields, and no authoritative semantic choices.

Failure mode B

Hand-built semantic layers

Expensive domain work, long onboarding, repeated effort per customer, and maintenance burden whenever the source evolves.

Primary userSituationJob to be done
AI engineer or product teamRead-only access to an unfamiliar customer or internal databaseMake one bounded agent workflow accurate without reverse-engineering the whole domain
Example teamsVertical AI, consultancies, enterprise AI, BYOD SaaSSupport collections, finance, operations, claims, logistics, or customer-success agents
Example objective

The agent should answer questions about customers, invoices, payments, and outstanding balances.

Atlas uses this required input to rank relevant objects, constrain semantic generation, prioritize review, and compile the final task context.

05

Semantic claims and trust

Meaning is represented as an atomic, attributable, reviewable, versioned claim—not blended into a generated paragraph.

SEMANTIC CLAIMJSON
{
  "claim_type": "table_grain",
  "subject": "billing.invoice_hdr",
  "proposal": "One row represents one customer invoice.",
  "confidence": 0.91,
  "status": "inferred",
  "evidence": [
    "invoice_id is unique",
    "invoice_id is the primary key"
  ]
}
Claim vocabulary

Interpretations the system can challenge

  • purpose, entity, and table grain
  • field meaning and canonical identifiers
  • relationship and lifecycle meaning
  • enum and business-rule definitions
  • sensitive-data classification
  • agent guidance and authoritative fields
Trust stateDefinitionAgent behavior
observedDeterministically true from source metadata or measured dataUse directly within evidence scope
inferredSemantic interpretation supported by evidenceUse in low-risk contexts with provenance
validatedConfirmed by a reviewer or authoritative evidenceUse for governed reasoning
unresolvedThe system knows it cannot settle the meaningClarify or avoid
staleSource change may have invalidated the claimRevalidate or block affected capability
conflictedEvidence or approved interpretations disagreeEscalate explicitly
06

Automated falsification

Atlas should try to disprove its own hypotheses before spending human attention.

Hypothesis

invoice.paid_at represents the date the invoice became fully paid.

Typed checks

Ask deterministic questions

  • Paid timestamp with non-paid status?
  • Matches final payment allocation?
  • Refunded invoices still populated?
  • Partially paid invoices populated?
Structured result

Update confidence and evidence

  • assertion and observed result
  • scope, verdict, and limitations
  • query ID or hash
  • snapshot version and freshness

The agent proposes a typed hypothesis. Deterministic Atlas code compiles adapter-specific SQL, executes it read-only, evaluates the result, and stores structured evidence. Free-form agent SQL is not the validation boundary.

09

Living model: drift and learning

The layer stays correct as the source changes and becomes more useful as agents encounter real ambiguity.

Source drift

Revalidate affected meaning

  • new or removed objects and fields
  • type, enum, constraint, and relationship changes
  • null, cardinality, and distribution shifts
  • mark impacted claims stale
  • identify affected agent capabilities
Usage feedback

Capture operational ambiguity

  • missing concepts or competing fields
  • failed SQL and tool plans
  • agent clarification requests
  • human answer corrections
  • context missing from the semantic graph
Reusable semantic memory

If “current contract value” could mean three fields, Atlas escalates rather than guesses. Once a reviewer defines it as annual_contract_value for active-customer questions, that correction becomes organization-specific operational knowledge.

10

MVP definition

Prove that a generated and lightly validated semantic layer improves one bounded agent workflow over raw-schema access.

In scope

PostgreSQL to task context

  • read-only connection or schema dump
  • privacy-safe profiling and required objective
  • relevance, entities, grain, relationships
  • claims, confidence, evidence, contradictions
  • ranked review queue and review decisions
  • semantic JSON and context compiler
Explicitly out of scope

Do not dilute the proof

  • universal connector coverage or ontology
  • full text-to-SQL or BI metrics product
  • writes, complex lineage, or graph database
  • large RBAC system
  • autonomous business-definition approval
  • broad unstructured-document ingestion
Fourteen-step MVP user flow

Create project → define objective → connect PostgreSQL → snapshot → profile relevant fields → rank tables → generate claims → run contradiction checks → review consequential questions → publish semantic graph → ask sample questions → compile context → compare against raw-schema baseline.

Early success criterionExpected behavior
CompressionHundreds of tables become a small relevant subgraph.
Structural validationHigh-confidence grain and relationship claims are checked automatically.
Human attentionFewer than approximately 20 consequential review questions.
Agent effectTask accuracy materially improves against the baseline.
Safe failureThe system identifies meaning it cannot infer safely.
MemoryReviewer decisions are preserved and reused.

12

Differentiation and moat

Connectors, browsing, ER diagrams, generated descriptions, MCP access, and raw text-to-SQL are features or adjacent categories—not the differentiated product loop.

Not the moat

Commodity capabilities

  • database connectors
  • schema browsing and diagrams
  • LLM-generated documentation
  • generic cataloging and MCP connectivity
Durable asset

Accumulated reasoning memory

  • source evidence and claim history
  • domain priors and human corrections
  • representative examples and agent failures
  • drift history and organization-specific language
Operational knowledge example

When a collections agent asks “amount owed”: use invoice.balance_due, exclude voided invoices, include posted credits, use account currency, and flag unapplied payments separately.

14

Product principles and north star

The product should unlock trusted agent reasoning with the least human semantic work.

#PrincipleConstraint
01Never hide uncertaintyUnknown is represented explicitly, never converted into confident prose.
02Separate observation and inferenceThe UI and runtime preserve the boundary.
03Human attention is scarceReview the highest-impact ambiguity, not every object.
04Objective shapes the modelDo not model the database uniformly.
05Prefer minimal sufficient contextServe only what the task requires.
06Semantics are falsifiableTest generated claims wherever possible.
07The model is livingSource drift, corrections, and failures update it.
08Fail safelyTell the agent what is missing instead of guessing.
North-star question

How much trusted agent reasoning can we unlock with the least human semantic work?

Source-adapter and security appendix

Adapters. PostgreSQL first; Snowflake, BigQuery, MySQL, SQL Server, Databricks, Salesforce, REST APIs, tabular exports, and suitable document stores later. Each adapter owns source-specific connection, quoting, extraction, profiling, read-only setup, timeouts, query IDs, and check execution.

Security defaults. Read-only source access, no customer writes, local profiling where possible, sensitive-field detection, identifier masking, email/phone/address redaction, no free-text samples by default, summarized distributions, and configurable per-field sampling policy.
